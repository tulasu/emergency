dispatcher/ — ядро заявителя с нуля

Context

Нужен механизм, который на вопрос оператора 112 отвечает фактом из описания
ситуации, быстро и офлайн, потому что дальше он встаёт в SIP-конвейер
VAD → STT → понимание → TTS. Ответы конечны и известны заранее, поэтому
задача не генеративная, а классификационная: реплику надо отнести к одному из
известных сведений либо честно отказать.

Данные для этого уже собраны в new_core/trainer/ и переезжают в новое ядро
как есть:

- scenarios/\*.json — 96 сценариев, 810 фактов, 7461 формулировка вопроса;
- blind/\*.txt — 101 слепой набор, 6011 реплик оператора (6 файлов \_v2 —
  второй независимый набор для тех же шести сценариев);
- core/bilets.md — первоисточник: 32 билета по три вызова.

Код ядра пишем заново. У старого new_core/trainer/caller/ две проблемы,
которые лечатся только переписыванием:

1. Каждый сценарий — замкнутый мирок. 303 разных ключа на 810 фактов,
    при этом место встречается 70 раз, телефон 59, фио_заявителя 43 —
    по смыслу одно и то же. Классификатор в каждом сценарии учится с нуля на
    ~8 фактах, хотя формулировок одного и того же слота по корпусу накоплены
    десятки. Отсюда потолок: медиана 60% по work/sweep.txt.
2. Нечем мерить. Метрика в work/sweep.py считает «долю реплик, на которые
    выдан хоть какой-то факт». Правильный факт от неправильного она не отличает,
    а для тренажёра выдать не тот факт хуже, чем сказать «не знаю»: обучающийся
    запишет в карточку ложные данные и будет уверен, что всё верно.

Старые core/ и new_core/ остаются нетронутыми — как справочный материал
и как точка сравнения в бенчмарке.

Главная идея нового ядра

Классификация идёт не по фактам сценария, а по общей онтологии слотов.

реплика → слот (addr.street, victim.count, caller.phone, access.code …)
→ факт текущего сценария, привязанный к этому слоту
→ нет такого факта → «не знаю» (и это правильный ответ)

Что это даёт:

- один классификатор на все 96 сценариев вместо 96 независимых;
- банк формулировок слота — это все формулировки этого слота по всему корпусу
  (4378 уникальных строк вместо ~9 на факт). Необычно заданный вопрос попадает
  в цель, потому что за слот «адрес» проголосовали десятки сценариев;
- бесплатные хард-негативы: вопрос про слот, которого в текущем сценарии нет, —
  это готовый размеченный «не знаю»;
- новый сценарий работает сразу, без дописывания вопросов вручную.

Онтология — ~40–60 слотов. data/ontology/slots.yaml: id, человекочитаемое
имя, тип (значение / да-нет / описание), aliases — список старых ключей,
общие формулировки. Компиляция раскладывает 303 ключа по слотам: сначала по
таблице алиасов и группам, остаток — вручную, с отчётом о неразложенном.
Цель — меньше 5% ручной работы.

Слоты обязаны быть достаточно дробными, чтобы в одном сценарии не оказалось
двух фактов на слот: addr.street, addr.building, addr.refined,
addr.landmark — разные слоты. Там, где это всё же случается, спор решает
свойство раскрытия (ниже).

Механика «в скобках». В bilets.md курсивом помечены уточнения, которые
заявитель называет только по прямому вопросу, — это главная учебная механика,
20 вызовов из 96. В новом ядре это свойство факта первого класса:
disclosure: on_request | volunteered, а не побочный эффект поля requires.

Расширение: новые ситуации от пользователя

Ситуации будут добавляться дальше, поэтому расширение — не побочный сценарий,
а основной режим эксплуатации ядра. Сейчас это самое дорогое место: по
PROMPT_scenario_draft.md автор обязан написать 8–13 перефразировок на
каждый факт (так и набрались 7461 формулировка вручную), а потом собрать
слепой набор и прогнать eval, чтобы понять, что получилось. На практике
этого никто делать не будет.

Слоты снимают ровно эту работу: формулировки принадлежат слоту, а не факту.

Случай А, обычный — все факты ложатся на существующие слоты. Автор пишет
только содержание: описание ситуации, факты (слот + текст ответа + стили
short/confirm/correct), флаг disclosure, список критичных.
Перефразировки не пишет вообще — их уже дали 96 сценариев до него.

python -m dispatcher.cli scenario new drafts/my_case.json # валидация + раскладка по слотам
python -m dispatcher.cli build --incremental # секунды: кодируются только новые строки

Случай Б — нужен слот, которого нет. Компилятор не может разложить факт и
показывает ранжированный список ближайших существующих слотов (косинус между
описанием факта и банками слотов). Автор либо выбирает из списка, либо заводит
новый слот: id, имя, тип и 5–8 затравочных формулировок. Инструмент времени
разработки дописывает к ним перефразировки моделью и показывает автору на
утверждение — один раз, офлайн, в рантайме этого нет. Новый слот попадает в
slots.yaml с пометкой версии, в которой появился.

Случай В — два факта одного сценария попали на один слот. Это ошибка
сборки, а не предупреждение. Разрешается либо разделением слота
(addr.street / addr.refined), либо различающим disclosure — именно так
устроено уточнение «в скобках»: обычный адрес и уточнённый адрес живут в разных
слотах, и второй выдаётся только по прямому вопросу.

Чем это удерживается от расползания:

- Регрессия при каждом расширении. Новый слот меняет ландшафт оценок:
  он может перетянуть на себя реплики соседнего. Поэтому build прогоняет
  замороженный gold-набор и печатает дельты по каждому затронутому слоту.
  Падение точности на существующих сценариях сверх допуска — отказ записать
  артефакты, обойти можно только явным --force.
- Пороги не трогаются при добавлении сценария. Перекалибровка — отдельная
  явная команда, после которой обязателен полный прогон бенчмарка.
- Линтер для автора вместо слепых наборов: scenario lint генерирует для
  каждого факта N отложенных перефразировок, проверяет, что классификатор
  попадает в нужный слот, и показывает факты со слабым покрытием —
  «у этого слота мало формулировок, допишите». Это замыкает цикл качества на
  авторе, не требуя от него собирать слепой набор на 60 реплик.
- Инкрементальная сборка. Векторы кэшируются по хэшу строки, добавление
  сценария перекодирует только новые формулировки.
- Горячая перезагрузка. Runtime.reload() подхватывает новые артефакты без
  перезапуска SIP-службы; звонки в работе доигрывают на своём снимке.
- Переименования без правки данных. aliases в slots.yaml держат старые
  имена ключей, поэтому онтологию можно чистить, не трогая 96 сценариев.
- Дубли в корпусе. Билет 1 №2 и билет 21 №1 совпадают полностью, ещё
  несколько вызовов делят адресный блок. В банке слота формулировки дедуплицируются,
  иначе повторы получают двойной вес.

Каскад понимания

Четыре слоя, каждый следующий дороже и вызывается реже.

Слой 0 — кэш. Нормализованная фраза → слоты, словарь на диске. 0 мс,
покрывает повторяющиеся формулировки, которых в речи операторов много.

Слой 1 — правила. Микросекунды, детерминированно:

- речевые акты: «бригада выехала», «оставайтесь на линии», «не подходите»;
- тип реплики: вопрос / переспрос / утверждение;
- числа в реплике сверяются со значениями фактов — мягкий буст к score,
  не жёсткий фильтр (в старом коде это был фильтр, и редкое число выбрасывало
  верного кандидата);
- эллипсис: «а точнее?», «а корпус?», «какой именно?», голая именная
  группа в 1–3 слова. Поиск ограничивается семейством слотов последнего
  отвеченного (addr.\*), порог опускается. Это и есть контекстные вопросы,
  зависящие от предыдущего ответа.

Слой 2 — би-энкодер. Основная работа.

- банк: формулировки каждого слота по всему корпусу, векторизуются один раз
  на сборке в build/bank.npz с хэшем источника;
- score слота = максимум косинуса по его формулировкам (max-pooling, не
  центроид: формулировки внутри слота разнородные);
- сплав с лексикой: s = α·cos + (1−α)·lex, где lex — пересечение лемм,
  взвешенное IDF. Слои дополняют друг друга: лексика берёт редкие точные слова
  («госномер», «Грина»), эмбеддинги берут перефразировки;
- составной вопрос режется на сегменты, ключи объединяются; добираются все
  кандидаты в пределах δ от лидера — оператор часто спрашивает о двух вещах разом.

Слой 3 — отказ или арбитр. Два порога, откалиброванных под долю ложных
фактов ≤2%:

- s ≥ τ_hi → отдаём;
- τ_lo ≤ s < τ_hi → серая зона, идём в локальную LLM;
- s < τ_lo → «не знаю».

Арбитр получает выбор из пяти, а не открытую классификацию: реплика +
top-5 слотов с одним примером вопроса на каждый + вариант «НИЧЕГО». Промпт
~150 токенов, ответ ~5. Открытую классификацию по всему каталогу модель на
0.6B не вытянет, выбор из шести литералов — вытянет. Вывод зажимаем
GBNF-грамматикой: ни парсинга JSON, ни срывов формата.

Текст ответа при любом исходе берётся из сценария. Модель работает только
классификатором и физически не может ничего сочинить — это свойство
архитектуры, которое надо сохранить при переписывании.

Потоковый интерфейс и текстовые тесты

Один и тот же код под двумя входами, чтобы тесты в тексте были честными:

rt = Runtime.load("data/build") # модели и банк грузятся один раз на процесс
s = rt.session("bilet04_call01")

s.on_partial("на каком эт") # спекулятивно считаем слои 0–2
s.on_partial("на каком этаже гор")
reply = s.on_final("на каком этаже горит") # чаще всего уже посчитано

s.say("на каком этаже горит") # текстовый режим = on_final без частичных

Спекуляция: на каждой частичной гипотезе гоняем дешёвые слои и запоминаем
результат по префиксу. Если top-1 стабилен на двух подряд гипотезах и попал
в серую зону — заранее дёргаем арбитра, чтобы его задержка спряталась внутри
ещё не договорённой фразы оператора. На финале, если текст совпал с последней
гипотезой, ответ отдаётся мгновенно; если нет — пересчёт, это всё равно ~10 мс.

s.cancel() — barge-in: снимает спекулятивную работу и возвращает id
проигрываемой реплики, чтобы медиа-слой её оборвал.

render возвращает audio_id рядом с текстом. Сам TTS в этот заход не входит
по решению пользователя, но место под него есть с первого дня.

Разметка и измерение

Делаем первым: без этого остальное непроверяемо.

1. bench/label.py — 6011 слепых реплик через сильную облачную модель: на вход
    каталог слотов сценария со всеми формулировками, на выход список слотов
    (пустой = заявитель этого знать не может). Пачками по ~20 реплик,
    temperature 0, ~300 вызовов на корпус, результат в data/gold/<id>.json.
    Нужен ANTHROPIC_API_KEY — в окружении он сейчас пуст.
2. bench/review.py — показывает 300 случайных размеченных реплик для ручной
    сверки и печатает долю расхождений. Эту цифру фиксируем как погрешность
    всех последующих измерений.
3. Разбиение: пороги и α подбираются на 2/3 сценариев, замораживаются, отчёт —
    на оставшейся 1/3 и на шести наборах \_v2 (билеты 1, 2, 5, 6, 8, 18).
    Мерить на том же наборе, по которому настраивались, бессмысленно: в старом
    README это уже отмечено как проверенная на практике ошибка.
4. bench/run.py печатает по каждой конфигурации: precision, recall, macro-F1
    по слотам, точность отказа, покрытие критичных фактов, долю реплик,
    дошедших до арбитра, p50/p95 латентности. Старый caller гоняется той же
    командой как базовая линия.

Арбитра меряем при прогретом KV-кэше системного промпта
(llama-server --parallel 1, переиспользование префикса). Холодный prefill
каталога на CPU — около секунды, с прогретым кэшем добивается только новая реплика.

Бюджет на ход, к которому идём: нормализация ~0.3 мс + кодирование 2–12 мс +
поиск ~0.1 мс + политика ~0.05 мс, p95 ≤ 20 мс на CPU и ≤ 8 мс на GPU.
Арбитр — на 10–20% ходов, p95 ≤ 250 мс CPU / ≤ 60 мс GPU, и его задержка
прячется спекуляцией. Для ориентира: нынешний лексический разбор — 0.67 мс.

Оговорка по железу

lspci видит RTX 4050 Max-Q, libcuda.so.595.84 на месте, но модуль ядра не
загружен: /dev/nvidia\* и /proc/driver/nvidia отсутствуют, nvidia-smi
падает. Скорее всего дискретка усыплена (Optimus) либо не видна из песочницы.
Первый шаг GPU-ветки — проверить nvidia-smi в обычном терминале
(! nvidia-smi). Если GPU не поднимется, CPU-ветка самодостаточна: ONNX int8
даёт нужные единицы миллисекунд, а арбитра придётся держать на 0.6B.

Диска 653 ГБ, huggingface.co доступен, ollama и llama.cpp не установлены —
ставим в рамках работы. Зависимости ядра: pymorphy3, razdel, numpy,
onnxruntime, tokenizers; опционально torch+CUDA и llama-cpp-python.

     Живой диалог руками обязателен помимо цифр:

     - контекстная цепочка «какой адрес» → «а номер дома?» → «а корпус?»;
     - вопрос вне сценария — должно быть «не знаю», а не «повторите»;
     - переспрос с неверным числом — должно быть исправление;
     - уточнение «в скобках» не выдаётся, пока о нём прямо не спросили;
     - replay --stream гоняет тот же диалог через частичные гипотезы и обязан дать
       тот же результат, что текстовый режим;
     - новая ситуация, заведённая без единой перефразировки, отвечает на вопросы,
       а build показывает, что точность на старых сценариях не просела.

     Считаем сделанным, когда на held-out и на _v2: recall по слотам заметно выше
     базовой линии старого ядра, доля ложных фактов ≤2%, p95 понимания укладывается
     в бюджет выше, а потоковый и текстовый режимы дают совпадающие ответы.
