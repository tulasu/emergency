# Шаг 3. SIP-сигналинг на Asterisk — план

Статус: только план, кода и конфигов в этом шаге нет.
Граница шага: сигналинг и прокидка `scenario_id` в медиа-сервис.
STT/TTS/RTP-обвязка медиа-сервиса — следующий шаг.

## Схема

```
Trainer UI / тест
  │  POST /calls {to, scenario_id}
  ▼
calls-gateway (тонкая прослойка, ~50 строк)
  │  ARI: POST /ari/channels {endpoint, variables: {scenario_id, call_id}}
  ▼
Asterisk (chan_pjsip, только сигналинг + RTP-терминация)
  │  dialplan: Stasis(trainer, ${scenario_id}, ${call_id})
  ▼
медиа-сервис (Session из dispatcher + STT/TTS, держит состояние звонка)
```

Asterisk не знает про сценарии. Всё, что он несёт, — две channel-переменные.
Вся логика звонка (какой сценарий, что ответить) живёт в медиа-сервисе.

## 1. chan_pjsip: регистрации

- Транспорт: один UDP-транспорт. TCP/TLS — не в этом шаге, добавить когда
  потребует сеть заказчика.
- Endpoints стажёров: `aor` + `auth` (digest) + `endpoint` на каждого
  (софтфон / симулятор оператора). Регистрации держит Asterisk, медиа-сервис
  их не видит.
- Внешний транк (если звонки уходят за пределы стенда): один `registration`
  + `identify`. На первом этапе может не понадобиться — звонки внутри стенда.
- Кодеки: только `alaw` (ТфОП — A-law). Запрет транскодинга в Asterisk —
  это и есть верхняя граница его потолка (см. п. 6).

## 2. Originate: POST /calls → ARI

Контракт наружу (единственная ручка шага):

```
POST /calls { "to": "101", "scenario_id": "bilet04_call01" }
→ 202 { "call_id": "<uuid>" }
```

`calls-gateway` внутри делает:

1. Проверяет `scenario_id` против списка сценариев (нет такого — 404,
   звонок не originates, Asterisk не дёргаем).
2. Генерирует `call_id`, кладёт в ответ и в channel-переменные.
3. `POST /ari/channels`:
   `endpoint=PJSIP/<to>`, `context=trainer-out`, `extension=s`,
   `variables={scenario_id=..., call_id=...}`, `app=trainer`.
4. Возвращает `call_id` сразу, дальше — по ARI WebSocket-событиям
   (StasisStart / ChannelDestroyed) для статуса звонка.

Основной путь — ARI: originate, события и Stasis-управление в одном API.
AMI (`Originate`) — только запасной на случай недоступности ARI, отдельных
сценариев под него не проектируем.

## 3. Dialplan: прокидка в медиа-сервис

```ini
[trainer-out]
exten => s,1,NoOp(call ${call_id} scenario ${scenario_id})
 same => n,Stasis(trainer,${scenario_id},${call_id})
 same => n,Hangup()
```

- `Stasis(trainer, ...)` отдаёт канал в ARI-приложение медиа-сервиса.
  Медиа-сервис читает `scenario_id` из ARI-события `StasisStart`
  и открывает `Session.open(scenario_id)` — тот же `Session`, что уже
  покрыт тестами (`session.py`), без нового кода состояния.
- Аудио между Asterisk и медиа-сервисом — ExternalMedia/UnicastRTP
  (RTP-сокет медиа-сервиса, Asterisk шлёт туда G.711).
  Запасной вариант — AudioSocket (проще парсить, но внестандарт).
- `Dial(SIP/медиа-сервис)` как SIP-хоп не используем: лишний хоп,
  лишний SDP, нечего выигрывать — Stasis уже даёт канал в руки.

## 4. Почему не свой Go-B2BUA на первом этапе

Свой B2BUA — это свой SIP-стек: ретрансмиты, SDP-переговоры, NAT,
digest-auth, регистрации, дальше TLS/SRTP; плюс RTP: jitter-буфер,
DTMF, RTCP. Это месяцы работы и баги в сигналинге вместо работы над ядром
и медиа. Asterisk даёт всё готовым плюс `sngrep`/pcap-отладку из коробки.

Цена Asterisk известна заранее (ресерч scout): один инстанс держит
~200–500 параллельных звонков (низ — с транскодингом/записью, верх —
G.711 без транскодинга, наш случай). Учебному стенду этого хватает с запасом.
Свой B2BUA становится темой, только когда упрёмся в этот потолок.

## 5. Потолок и рост: Kamailio + ферма

- Триггер: CPU Asterisk / RTP-loss при росте параллельных (мерим `sipp`,
  см. приёмку). Не раньше.
- Схема роста: Kamailio спереди (registrar + dispatcher/балансировщик),
  за ним ферма одинаковых Asterisk. Kamailio — stateless-прокси, состояние
  звонка (Session, scenario_id) живёт в медиа-сервисе, поэтому Asterisk
  горизонтально масштабируется без переделки шага 3: `calls-gateway`
  выбирает инстанс, dialplan и переменные те же.
- В этом шаге под Kamailio ничего не пишем — только не закладываем
  состояние в Asterisk (см. схему: две переменные, и всё).

## 6. Приёмка шага (когда дойдём до внедрения)

1. `sngrep`: `POST /calls` → INVITE → 200 OK → RTP → BYE, без ошибок.
2. `scenario_id` доехал: медиа-сервис открыл нужный сценарий, стажер
   слышит его `opening` (сверка с `cli chat <scenario_id>`).
3. Неизвестный `scenario_id` → 404, звонка нет.
4. Обрыв стажёром → `ChannelDestroyed` → сессия закрыта, без висяков.
5. `sipp`: N параллельных, фиксируем, где начинается деградация, —
   это паспорт потолка до Kamailio.

## Порядок внедрения (не в этом шаге, зафиксировано чтобы не потерять)

1. `pjsip.conf`: транспорт + 2–3 тестовых endpoint'а.
2. `extensions.conf`: контекст `trainer-out` из п. 3.
3. `calls-gateway`: валидация + ARI originate + минимум событий.
4. Ручной звонок с софтфона → сверка `opening` со сценарием.
5. `sipp`-прогон → паспорт потолка.
